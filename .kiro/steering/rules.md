# kaji-app 開発ルール

## セキュリティ制約
- 外部サーバー（Firestore等）に送信するデータは必要最小限に絞ること
- アップロードされたファイルをそのままサーバーに保存しない
- 新しいファイルをアップロードする機能を追加する際は、リモートに送信するデータを事前に明示し確認を取ること
- 個人情報（氏名・会員番号・カード番号・住所など）は読み取り自体しない

## コスト制約
- Firebase Sparkプラン（無料枠）の範囲内で運用する
- 従量課金が発生するサービスは事前に確認を取ること
- 外部ライブラリはCDN経由のscriptタグで読み込む（ビルド環境不要を維持）

## 構成ルール
- index.html 1ファイルにHTML/CSS/JSを全部収める
- データ保存はFirestore + localStorageフォールバック
- 認証はGoogleログイン（post.usnv777@gmail.com / g1712060@gmail.com のみ許可）
- GitHub Pages でホスティング（https://postusnv777.github.io/kaji-app/）

## コード規約
- 日本語UIで統一
- スマホファーストのレスポンシブデザイン
- PWA対応を維持する

## レビューペルソナ

コード変更時は以下のペルソナ視点でセルフレビューを行うこと：

### 🔒 セキュリティレビュアー
- 立場: 過去にAPIキー漏洩でインシデント対応した経験のあるインフラエンジニア
- 性格: 疑い深い。「本当に送る必要ある？」が口癖
- 観点:
  - Firestoreに送信するデータは必要最小限か（SECURITY.md準拠）
  - 個人情報（氏名・カード番号等）が混入していないか
  - UIの説明文と実際のデータフローが一致しているか

### 📱 UI/UXレビュアー
- 立場: スマホしか使わない非エンジニアの主婦/主夫。ITに詳しくない
- 性格: 直感的に使えないとすぐ諦める。説明書は読まない
- 観点:
  - タップしやすいか（44px以上のタッチターゲット）
  - 画面を見ただけで何をすればいいか分かるか
  - 色だけで情報を伝えていないか（色覚多様性）
  - 表示テキストが技術用語になっていないか

### 💰 コスト・運用レビュアー
- 立場: Firebase無料枠を使い倒してきた個人開発者
- 性格: 1円でも課金が発生すると夜眠れない
- 観点:
  - Firestoreの読み書き回数が不必要に増えていないか
  - 無料枠を超える可能性のある変更はないか（dev-policy.md準拠）
  - localStorageとFirestoreの同期設計に無駄がないか

### 🧑‍💻 コード品質レビュアー
- 立場: 10年以上の経験を持つフロントエンドエンジニア。コードレビューが日課
- 性格: 「動けばいい」が許せない。命名・構造・一貫性にこだわる。技術的負債を生む変更には必ずコメントする
- 観点:
  - 関数名・変数名が意味を正確に表しているか
  - 同じパターンの処理が統一された書き方になっているか（既存コードとスタイルが揃っているか）
  - 1つの関数が1つの責務に収まっているか（巨大関数になっていないか）
  - マジックナンバーや重複コードがないか
  - データフォーマットの変換は一箇所で行い、アプリ内部では統一フォーマットを使っているか
  - エッジケース（空値、不正入力、データ未存在）を適切に処理しているか
  - 将来の変更に耐える設計か（カード種別追加・カテゴリ追加時に修正箇所が最小か）
